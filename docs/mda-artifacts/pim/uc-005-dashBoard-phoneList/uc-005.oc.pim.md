## Purpose

Operation Contracts formalize the **system operations** identified in the System Sequence Diagram. Each contract specifies the operation's preconditions and postconditions in terms of the PIM Domain Model.

These contracts are **platform-independent**. They describe what changes in the system's state, not how the change is implemented.

Source: Craig Larman, *Applying UML and Patterns*, Chapter 12.

## Contract OC-001: getPhoneListForActiveShift

**Operation:** `getPhoneListForActiveShift() : List<PhoneAssignment>`

**Cross References:** UC-005 "View phone list for active shift"

**Preconditions:**
- The system holds the fixed set of work phones for Slottet
- The active shift is identifiable

**Postconditions:**
- A list of PhoneAssignment instances for the active shift is returned
- If no assignments exist for the active shift, an empty list is returned
- No system state is modified (query-only operation)

---

## Contract OC-002: selectShift

**Operation:** `selectShift(shiftType : ShiftType) : List<PhoneAssignment>`

**Cross References:** UC-005 "Assign caregiver name to phone" — main flow step 1

**Preconditions:**
- `shiftType` is a valid value from the ShiftType enumeration (Day, Evening, Night)

**Postconditions:**
- The selected shift context is established for subsequent operations
- A list of PhoneAssignment instances for the selected shift is returned
- No persistent system state is modified

---

## Contract OC-003: assignPhone

**Operation:** `assignPhone(phoneNumber : String, caregiverName : String, shiftType : ShiftType) : PhoneAssignment`

**Cross References:** UC-005 "Assign caregiver name to phone" — main flow steps 3–6

**Preconditions:**
- `shiftType` is selected (not null)
- `phoneNumber` belongs to the fixed set of Slottet work phones
- `caregiverName` is not empty
- `shiftType` is a valid value from the ShiftType enumeration

**Postconditions:**

*On success:*
- A new PhoneAssignment instance was created with:
  - `phone.number == phoneNumber`
  - `caregiver.firstName + caregiver.lastName == caregiverName`
  - `shiftType == shiftType`
  - `assignedAt == current system time`
- The new PhoneAssignment was associated with its Phone, Caregiver, and ShiftType (Rule M3)
- The system state now reflects the new assignment

*On business rule violation:*
- No PhoneAssignment was created
- The system state is unchanged
- An error indication is returned

*Invariants enforced (Rule M5):*
- At most one PhoneAssignment exists for the (phoneNumber, shiftType) combination
- At most one PhoneAssignment exists for the (caregiverName, shiftType) combination

---

## Contract OC-004: clearAssignment

**Operation:** `clearAssignment(phoneNumber : String, shiftType : ShiftType) : void`

**Cross References:** UC-005 "Clear assignment"

**Preconditions:**
- `phoneNumber` belongs to the fixed set of Slottet work phones
- `shiftType` is a valid value from the ShiftType enumeration
- A PhoneAssignment exists for the (phoneNumber, shiftType) combination

**Postconditions:**

*On success:*
- The PhoneAssignment for (phoneNumber, shiftType) no longer exists in the system state
- Other PhoneAssignments are unaffected
- The Phone and Caregiver entities themselves are unchanged

*On precondition failure:*
- The system state is unchanged

---

## Contract OC-005: refreshPhoneList

**Operation:** `refreshPhoneList() : List<PhoneAssignment>`

**Cross References:** UC-005 "Automatic refresh (System Time Event)"

**Preconditions:**
- The system is operational
- The active shift is identifiable

**Postconditions:**
- Current PhoneAssignment instances for the active shift are returned
- No system state is modified (query-only operation)
- The operation is idempotent (repeated calls produce equivalent results)

## What These Contracts Do NOT Specify

These are **PIM-level** contracts. The following are deliberately omitted:

- **No platform technology** — no HTTP methods, no REST URLs, no SQL
- **No data types** — no `Guid`, `string`, `Task<T>`, `IEnumerable<T>`
- **No async semantics** — synchronous specification only
- **No persistence mechanism** — "system state" is abstract, not "database row"
- **No exception types** — error indications are abstract concepts
- **No authentication/authorization** — handled by separate use cases (UC-004)

These concerns appear in the PSM operation contracts (or equivalent design artifacts).

## Validation

Each contract should be:
- **Testable:** Given preconditions, the postconditions can be verified
- **Complete:** All system operations from the SSD have a contract
- **Consistent:** Contracts do not contradict the domain model or use case
- **Platform-independent:** The contract is valid for any implementation technology

---

## Maintenance

- Update when system operations change in the SSD or use case
- Ensure invariants stay aligned with business rules from CIM
- Validate that all PIM types (UUID, String, DateTime, Enumeration) are used consistently
