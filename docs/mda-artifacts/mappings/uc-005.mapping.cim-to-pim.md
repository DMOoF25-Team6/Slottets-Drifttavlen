## Purpose

This document specifies the **transformation rules** for converting the Computation Independent Model (CIM) of UC-005 into a Platform Independent Model (PIM).

The CIM describes **what the business needs**. The PIM describes **what the system must do** to satisfy that need, without committing to any platform. This mapping document is the bridge between the two.

In a fully automated MDA toolchain, these rules would be machine-executable. In this project they are documented manually as **traceability evidence** between abstraction levels.

---

## Transformation Philosophy

CIM → PIM is the step where **a system is introduced into the conversation**.

Before this transformation:
- The world contains only business actors and business activities
- "Slottet" is a building, "Caregiver" is a person, "Work Phone" is an object

After this transformation:
- A new abstract actor exists: **the system**
- Business activities become **system interactions**
- Business relationships become **system entities**

The transformation does NOT yet introduce technology. No .NET, no databases, no UI. That comes in CIM → PSM.

## Mapping Rules

### Rule M1: Business Actor → System Actor

| CIM | PIM | Reason |
|---|---|---|
| `Caregiver on Shift` | `Caregiver` (system role) | The system needs to identify and authenticate the caregiver |
| `Shift Coordinator` | `Shift Coordinator` (system role) | Different access rights than a regular caregiver |
| — | `System Time Event` (new actor) | Time-based behavior is a system concern; the actor doesn't exist in CIM |

**Transformation reason:** A business person can act in different roles depending on context. The system formalizes these as role-actors with specific permissions.

---

### Rule M2: Business Goal → System Use Case

| CIM Goal | PIM Use Case |
|---|---|
| "See which caregiver carries which work phone for this shift" | "View phone list for active shift" |
| "Take responsibility for a work phone during my shift" | "Assign caregiver name to phone for selected shift" |
| "Release my work phone at end of shift" | "Clear assignment for phone in selected shift" |
| "Identify which caregiver to contact for a resident concern" | (covered by 'View phone list') |

**Transformation reason:** Each business goal must be satisfied by one or more system interactions. The PIM use case is more concrete: it describes what the user does *with the system*, not just what they want to achieve.

---

### Rule M3: Domain Relationship → System Entity

This is the **most important transformation in this mapping**.

#### CIM (forretningsrelation):

```
Caregiver ─── carries on shift ──→ Work Phone
```

A simple relationship between two domain concepts. Both exist independently in the real world.

#### PIM (system entity):

```
Caregiver ─→ PhoneAssignment ←─ Phone
                  │
                  Shift
```

A new entity `PhoneAssignment` appears, capturing the *act of assigning* as a thing in itself.

**Transformation reason:** The system needs to remember assignments — who carried which phone on which shift. A pure relationship cannot be stored, audited, or queried. The system promotes the relationship to a first-class entity (`PhoneAssignment`) so it can be:
- Stored persistently
- Audited (who assigned, when)
- Queried (who carried phone X on shift Y last Tuesday?)
- Cleared without affecting the underlying concepts

This is a classic example of **CIM → PIM elevation**: a real-world relationship becomes a system-level entity because the system must remember things the real world simply *did*.

---

### Rule M4: Implicit Knowledge → Explicit System Behavior

| CIM (implicit) | PIM (explicit system behavior) |
|---|---|
| "Other caregivers can see who has each phone" | System displays current phone list when requested |
| "Assignments are per shift" | System filters phone list by selected shift |
| "Assignment can change mid-shift" | System supports updating assignments at any time |
| "End-of-shift release" | System clears or marks unassigned when name is removed |

**Transformation reason:** In the real world, knowledge is shared by talking, looking at paper, or just being present. The PIM must make this knowledge transfer explicit as system queries and updates.

---

### Rule M5: Business Rule → System Constraint

CIM business rules become PIM operation contracts (preconditions, postconditions, invariants).

| CIM Rule | PIM Constraint |
|---|---|
| "Each phone is carried by one caregiver per shift" | Cardinality: PhoneAssignment 1..* — 1 Phone per Shift |
| "A caregiver carries at most one phone per shift" | Cardinality: Caregiver 1 — 0..1 Phone per Shift |
| "Phone numbers are fixed" | Invariant: PhoneNumber values are constrained to a fixed set |
| "Shifts are Day/Evening/Night" | Invariant: ShiftType is a closed enumeration |

**Transformation reason:** Business rules in natural language become formal constraints the system must enforce.

## What This Mapping Does NOT Do

- **No platform decisions.** No mention of .NET, MySQL, REST, EF Core. Those decisions belong in CIM → PSM (or PIM → PSM via marks and mappings).
- **No UI decisions.** No screens, buttons, or input fields. That is also PSM territory.
- **No persistence strategy.** PIM says "the system must remember"; PSM says "use a MySQL database with EF Core".
- **No performance considerations.** "Every 60 seconds" is a PSM constraint, not a PIM concern.

---

## Validation Checklist

After applying this mapping, the resulting PIM should satisfy:

- [ ] Every CIM actor maps to one or more PIM actors
- [ ] Every CIM goal is covered by one or more PIM use cases
- [ ] Every CIM relationship is either preserved or elevated to a PIM entity
- [ ] Every CIM business rule is captured as a PIM constraint
- [ ] No technology-specific concepts appear in the PIM
- [ ] No UI-specific concepts appear in the PIM
- [ ] The PIM could be implemented in Java, .NET, Python, or any other platform
